## 0. 结论摘要

1. **iOS 已经不是"缺功能"，而是"链路有断点"**：单城市单次行程的规划、编辑、住宿、铁路、航班起价、接驳、导出已闭环；断点在 ①多城市/中途换住处 ②需要平台会话或商家凭据的额外实时报价渠道（默认已验证 RollingGo、12306 与飞猪 H5）③分享/导入/协作/足迹等第二曲线 ④基于未来日期的可靠数据（营业时间、天气、闭馆日）。
2. **规划器"傻"的根因是三层**：①移动时间用直线速度+固定开销估算（无路网）；②停留时长只看 6 个兴趣类型（不看人群、时段、规模）；③分配与排序是贪心（无局部搜索、无时间窗可行性检查）。这三层都可在不推翻现有"可解释启发式"的前提下升级。
3. **三平台同步的唯一解是决策下沉**：把规划编排、价格归一、排序、风险判断放进 Backend 的共享决策层，三端只渲染契约结果。否则 iOS 一套算法、Android 另一套，永远不同步（现在 Android 已经出现"每一版都落后 iOS 一整个版本"的问题——Android 0.4 连编辑、门票、PDF、直连价格都没有）。
4. **"实时价格都搞定"必须重定义为可验收标准**：渠道是否可达是外部依赖。1.0 的承诺是——凡配置齐全的渠道必须返回带来源、口径、抓取时间的价格；失败时用户能看到确切原因；至少两条独立渠道（非同一数据源）完成真实价格实测。做不到的渠道（无凭据/需商家合作）如实显示，不冒充。

### 1.3 Android 与 iOS 的差距（三平台同步的真实工作量）

Android 0.4 具备：欢迎、偏好、单城市规划、示例路线、住宿/交通/费用、节点报价、保存。**没有**：方案编辑（增删/拖动/撤销）、门票、PDF/ICS 导出、多通道直连价格、平台登录会话（只有入口）、智能向导、面板三档、景点挑选、跨天复制、版本历史。技术栈为 Compose + MapLibre Native（OSM 数据），与 iOS 数据模型为两套手写实现。

**结论**：Android 工作量的主体不是"翻译页面"，而是补齐"决策逻辑"。这正是把规划引擎下沉 Backend 的理由——Android 每项新功能都复用后端契约与金标样本测试。

## 2. 规划器为什么"傻"——根因与改造

### 2.1 根因

| 层 | 现状（依据：`ITINERARY_PLANNING_MODEL.md` + `TourismPlanningPolicy.swift`） | 后果 |
| --- | --- | --- |
| 移动时间 | 直线距离 × 速度（步行 4.5km/h、公交换 18km/h、驾车 27km/h）+ 固定开销；上限 120 分钟 | 跨江、绕行、等车全部失真；"移动 25 分钟"常常是错的 |
| 停留时长 | 6 类兴趣 × 3 档节奏 ×（主游览 1.28） | 同一景点带 4 岁娃 vs 情侣，时长一样；不看规模/时段/二次入园 |
| 分配算法 | 空间种子 + 最近贪心；日内近邻贪心 + 营业时间有限优先 | 无跨日交换改进；可选顺序常被首日顺序锁死 |
| 时间窗 | 只有"今日营业时间"单一窗口、无星期、无闭馆日 | 周一排闭馆博物馆；预约制景点无提示 |
| 人群画像 | 无（儿童/老人/体能/步速全缺） | 亲子与青年行程只是 150 分钟 vs 105 分钟的差别 |
| 天气 | 无 | 大雨天把园林排一整天 |
| 费用 | 大交通+住宿+接驳+门票明细；无总预算约束下的联合优化 | 预算紧时不会主动换酒店/交通 |
| 可解释性 | 每天有"为何这样展开"段落；但每条推荐缺少"为何" | 用户只能接受或整体跳掉 |

### 2.2 改造方案（保持"可解释启发式"，不追求全局最优）

**第一步：真实路网（1.0 的基石，先做）**
- Backend 新增 `/v1/routes`：输入坐标对列表+模式，返回距离/耗时矩阵。实现：高德 Web 服务路径规划（步行/公交/驾车，已有 Key 体系）为主，OSRM 开源实例为备（公交缺失时降级直线估算并标注）。
- 规划器所有移动分钟改读矩阵；MKDirections 结果回写缓存矩阵，避免重复查询。
- Android/Web 由此获得与 iOS 相同的移动时间语义（现在 Android 完全没有路网）。

**第二步：约束模型与本地搜索（不推翻现有结构）**
- 把每天建模为"时间窗 + 体力预算 + 营业窗口"的可行序列；顺序求解升级为：贪心初始解 → 受限 2-opt/跨日交换（每处移动只允许可解释提升，即"挪动后等待更短/路线更短"才采纳）→ 输出时附上"我为什么这样排"。
- 超载从"提示"升级为"自动降级方案 + 对比"：A 方案保留全部（偏赶）、B 方案精简（少 1-2 处），用户选。
- 每处停留时长参数化：基础时长 × 人群系数 × 时段系数 ×（规模/评分修正）；打开时间窗优先以"上午/下午/夜间"分组而非绝对分钟。

**第三步：画像与风险**
- 同行画像：儿童年龄（学龄前/小学生/大童）、老人同行、步速、是否带婴儿车。影响：停留时长、路线坡度、步行阈值、餐食节奏。
- 风险标记（只标记不假装）：周一闭馆、预约制、限流、临时闭馆（如果读到）、门票售罄状态、返程晚点缓冲。
- 天气：免费天气源（和风/Open-Meteo）按日预报；雨天自动"内景优先"，连续降雨给"改期"提示。

**第四步：多城市与住宿联动（M4）**
- 城市序列 → 每城 1-2 天（重点城多一天）→ 城际段自动插入高铁/航班候选（复用现有大交通查询）→ 城际耗时进入整体时间线。
- 支持"第 N 晚换住处"：生成换住日、寄存/搬运行李说明。

**第五步：预算联合（M4/M2 部分）**
- 总预算（加/人）下：住宿候选按（每晚价×晚数+交通+门票+每日市内）排序；把"超支风险"与"调整建议"（换酒店档位/改交通席别/减一天）给出 2-3 个选项。

**可解释性贯穿**：每个结构化建议带 reason 字段（距离/热度/时间窗/性价比/风险），三端统一渲染成"为什么要这样"。

## 3. 目标定义（1.0 的可测验收线）

### 3.1 旅程闭环（三端一致）
1. 一句话/表单 → （必要时）1-3 轮澄清 → 完整方案：每日时刻、地图路线、住宿、往返大交通、门到门接驳、费用、逐条理由。
2. 方案可编辑：增删、拖动、跨天移动/复制、改日期/人数/预算/节奏/交通偏好；**只重算受影响部分**（锁定项不跳动）。
3. 单城市与多城市（≤3 城，含中途换住处）都可生成、保存、恢复。
4. 输出：PDF、ICS、网页只读分享链接。
5. 版本历史：至少保留 3 个快照可回退。

### 3.2 实时价格闭环
6. 酒店：同房型跨渠道比价（≥3 渠道在配置齐全时）；房型/床型/早餐/取消/税费对齐；价格 7 天历史曲线；过期/登录/验证/限流/无房状态五态清晰。
7. 交通：铁路去返双程实时+席别价；航班至少 2 个独立渠道完成真实数字验收（飞猪已通过，去哪儿会话与携程节点待完成其一）。
8. 门票：3 个代表性城市覆盖率实测 ≥80%，未命中时明确"票价待查"。
9. 每条价格：渠道、口径（每晚/总价/人均）、抓取时间、锁价风险提示。

### 3.3 可靠性（三端同 fixtures）
10. 金标样本 ≥30 组：断网、过期、单渠道失败、无票、验证码、登录过期、空结果、酒店换选、忙碌铺松、跨城——三端输出同一业务状态。
11. 设备矩阵：iOS 17+/iPhone 与 iPad、Android 12+（arm64 真机 ≥2 台）、Web 桌面+移动；每端走查登录/加载/空/错误/刷新/返回/大字体/横竖屏。
12. 性能与无障碍：VoiceOver/TalkBack 全流程、大字体、弱网重试、冷启动 <2.5s、面板拖拽减少动态效果降级。

### 3.4 发布
13. iOS 无签名 IPA + tag + GitHub Release；Android 生产签名 + Play/侧载双通道说明；Web 部署到可访问域名（GitHub Pages 或自托管）。
14. 渠道健康卡（后端 `/health` 扩展为三端可见的"我的价格源状态"页面）：每个渠道 configured/disabled/login/verified/limited，用户可一键引导修复（打开登录页/填凭据）。

## 4. 架构决策（三平台同步的前提）

1. **规划下沉**：`POST /v1/plans`（输入：条件+候选+画像；输出：逐日方案+理由+风险）。iOS/Android/Web 同一契约。iOS 保留本机回退（离线或无节点时用现有简化启发式，并明确标注"本机估算"）。
2. **契约与金标**：OpenAPI + JSON Schema 入 `Contracts/`；CI 生成 Swift/Kotlin/TS 类型；`Fixtures/` 存 30 组金标输入-输出 JSON，三端测试共用。
3. **价格归一在服务端**：渠道矩阵、房型归一、历史曲线、健康状态都由 Backend 出；客户端只渲染 + 提供登录/重试入口。
4. **Web 最小闭环**：React + TS + Vite + MapLibre GL + PWA。功能面 = iOS 的 90%（无钥匙串登录、无 WebKit 会话；在线登录仍走平台网页，会话只留浏览器）。分享链接/网页预览由 Web 承载。
5. **Android 跟随**：每个里程碑把 Android 拉到同一契约版本（M1 起 Android 接 `/v1/plans`，顺带解决规划器与 iOS 不一致的问题）。

## 6. 每周工作流（研发闭环）

```
周一  契约评审：本周功能 → OpenAPI/Schema 变化 → fixtures 新增用例（先写失败样本）
周二-三  Backend：契约实现 → 单元测试 → 用 fixtures 自测
周四  三端实现：类型生成 → iOS/Android/Web 各自渲染 + 本机回退（如有）
周五  回归：fixtures 全量（三端）+ 模拟器主流程 + 真机抽查 1 项 → 发 build → 更新 CHANGELOG
```

固定纪律：
- **契约先行**：改协议先改 `Contracts/`，三端生成后再动 UI。
- **fixtures 是验收**：每个 bug 样本先进 fixtures 再修代码。
- **状态诚实**：渠道新增必须带 `disabled/disabled/unverified` 与原因；不允许"看起来有入口"。
- **每周末**：两个工作副本（`/Users/conrad/Documents/AnyTravel` 与 `/Users/conrad/Documents/ChatGPT/AnyTravel`）必须同步，防止接力时丢状态。

## 7. 风险与诚实边界

1. **外部凭据是硬依赖**：携程/同程依赖用户登录会话，艺龙需商家凭据+公网 IP 白名单，万邦需商家 key，高德需"Web 服务"类型 key。凡无凭据的渠道在 1.0 验收线中标记为"不可用（原因）"，不写承诺。
2. **真实价格 ≠ 成交价**：所有自动化价都是"展示价/起价"，最终以平台结算页为准；1.0 文案必须保留这一句。
3. **规划器升级不应推翻可解释性**：任何优化必须能生成"为什么这样排"；无法解释的增强不采纳。
4. **双倍工作量风险**：三端同步意味着每个功能 ×3；预算按 1.2 系数放大每项。
5. **Web 的会话与安全**：Web 不存平台密码；自定义 Key 只在浏览器会话内，明确风险提示（架构文档已定）。
6. **模拟器/静态验收不算完成**：每项功能至少一次真机主流程，金标 fixtures 之外的 bug 概率仍然存在。
